# autopg v3.2.0 — handoff for consumers on v3.0.7

> **Upgrade now.** v3.0.7 (2026-05-22) → v3.2.0 (2026-09-19). Every consumer of
> autopg — omni, genie, brain, anything that shells out to `autopg` or runs
> `autopg postmaster` — should move to v3.2.0 and drop the workarounds it
> carries for the problems listed below. v3.1.0 was tagged on 2026-09-02 but
> never published (see "Release integrity"); v3.2.0 contains it.

```bash
# host install (pins, verifies the cosign signature, runs `autopg install`)
AUTOPG_VERSION=v3.2.0 curl -fsSL https://raw.githubusercontent.com/automagik-dev/autopg/main/install.sh | bash

# already installed
autopg update

# container (omni-style Dockerfile): only the autopg version moves
--build-arg AUTOPG_VERSION=3.2.0     # PINNED_PG_VERSION is still 18.3.0-beta.17
```

Verify any tarball you fetch yourself:

```bash
cosign verify-blob \
  --certificate-identity-regexp '^https://github.com/automagik-dev/autopg/.github/workflows/sign-attest.yml@refs/tags/v.*$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  --signature autopg-3.2.0-<platform>.tar.gz.sig \
  --certificate autopg-3.2.0-<platform>.tar.gz.cert \
  autopg-3.2.0-<platform>.tar.gz
```

Platforms shipped: `linux-x64-glibc`, `linux-arm64`, `darwin-arm64`. No musl
build and no Intel macOS build, same as v3.0.7.

## What you gain

| Problem on v3.0.7 | What v3.2.0 does | PR |
|---|---|---|
| `autopg install` reported success while Postgres was still starting or had already died; pm2 said `online` for a dead postmaster | `install` and `restart` exit 0 only once the postmaster has published a live runtime record on the configured port, owned by the pm2 process; 30 s budget, exit 1 with the reason otherwise | #143 |
| `autopg restart` targeted the legacy `pgserve` pm2 name, missed the real process, and respawned an unmanaged daemon | restarts `autopg-server` under pm2 and waits for readiness; refuses on hosts another supervisor owns and names that supervisor's restart command | #143 |
| `autopg status` reported a stopped service as healthy | `status` reports readiness and pm2 state separately (see the JSON change below) | #143 |
| **After a pm2 daemon restart (`pm2 resurrect`, i.e. the `pm2 startup` unit at boot) autopg was gone** while its consumers came back and crash-looped against a closed port. Caused a ~30 h Omni outage (#144) | `install` runs `pm2 save` once the service is ready (only when the saved entry differs from the live one), reads the dump back to prove it, and exits 1 if it cannot; `uninstall` saves too (`--force`) so a removed entry does not come back; `autopg doctor` has a `pm2_persistence` check; `status --json` reports `persisted` | #152 |

## Behaviour changes to handle when you upgrade

1. **`autopg status --json`**: `status` is now `ready` \| `degraded` \| `stopped` \| `failed`,
   and `ready` is a boolean. pm2's raw state (`online`, `stopped`, `errored`)
   moved to `supervisorStatus`. Scripts that compared `status` to `"online"`
   must read `ready` instead. New fields: `supervisorStatus`, `persisted`.
2. **`autopg install` can take up to 30 s and can exit 1** where it used to return
   immediately with 0. Exit 1 means the service is not ready (message says why,
   logs at `~/.autopg/logs/autopg-server-error.log`) or its pm2 registration
   could not be made durable. Treat non-zero as "not usable yet", not as "not
   installed".
3. **`install` runs `pm2 save`** by default. That snapshots your whole pm2 process
   list, which is what an operator would do by hand after registering a
   service. Pass `--no-save` if you manage `pm2 save` yourself; the CLI then
   warns that the entry will not survive a resurrect.
4. **`autopg uninstall` prompts on a TTY.** Scripts must pass `--yes`.
5. **`autopg restart` requires pm2.** On a host whose `admin.json` records
   `systemd-user`, `launchd` or `external`, it exits 1 and prints that
   supervisor's restart command instead of spawning an unmanaged daemon.

## Release integrity (why v3.1.0 never reached you)

The release pipeline (`build-tarballs → sign-attest → release-publish`) used
GitHub `workflow_run` hops. Those never fire after a bot-dispatched build, and
even when they fire they run at `main`, producing signatures the trust list
(`sign-attest.yml@refs/tags/v.*`) rejects. Every release since v2.6.10 had been
finished by hand; v3.1.0 was not, so `releases/latest` and
`.well-known/latest.json` stayed on 3.0.7 for 17 days and `autopg update`
kept serving 3.0.7. Since #151 each hop is an explicit dispatch at the tag,
manual rebuilds of old tags cannot republish them, and the `latest.json`
commit fails the run loudly instead of warning. v3.2.0 is the first release
produced by that chain with no manual step.

Distribution facts that have not changed and that some repos still get wrong:

- Nothing has been published to npm since v3.0.0; `pgserve@2.6.10` is the last
  npm version and is legacy. The signed GitHub Release tarball is the only
  supported artifact.
- `install.sh` verifies with `gh attestation verify`, falling back to
  `cosign verify-blob`. If you fetch the tarball yourself (containers), verify
  the signature, not only the `.sha256` — the checksum proves integrity of the
  download, the signature proves who built it.

## Replace your custom fixes with the native mechanism

If your repo carries any of these, delete it and use the autopg verb:

| Custom fix you may have | Native since | Use |
|---|---|---|
| Sleep / retry loop after `autopg install` until `psql` connects | v3.2.0 | `autopg install` returns when ready; `autopg status --json` → `.ready` |
| `pm2 save` after installing autopg, or a boot script that re-registers it | v3.2.0 | nothing; `autopg doctor` reports `pm2_persistence` |
| Cron or watchdog that restarts autopg when connections hang | v3.2.0 | nothing; #153 removes the cause. Keep a watchdog only if you have evidence of another one |
| Restarting Postgres with `pm2 restart pgserve`/`autopg-server` directly | v3.2.0 | `autopg restart` (waits for readiness, exit code is meaningful) |
| Health check that parses `pm2 jlist` or `autopg status` text | v3.2.0 | `autopg status --json` → `.ready`, `.status`, `.supervisorStatus`, `.persisted` |
| Manual `CREATE EXTENSION vector` workaround or a pinned pgvector .deb | v3.1.0 | `runtime.enablePgvector=true` in `~/.autopg/settings.json` |
| `yes \| autopg uninstall` or `expect` around uninstall | v3.1.0 | `autopg uninstall --yes` |
| Downloading the tarball with only a sha256 check | always | verify the cosign signature (recipe above) or use `install.sh` |
| Building the connection string from a hard-coded port | always | `autopg url` / `autopg port` |

## For brain (`khal/brain`, checked against 2.41.0 / `5b208cd7`)

Brain takes autopg **latest** (nothing pins a version in `deploy-personal.sh`,
`scripts/install.sh` or `scripts/personal-macos.ts`), so its hosts move to
v3.2.0 on their next `autopg update` or deploy run. Two lines break when that
happens; everything else is either now redundant or already the target design.

### Breaks on v3.2.0 — change first

| Where | Today | Why it breaks | Change to |
|---|---|---|---|
| `deploy-personal.sh:116` | `jq -r '.status' == online` decides whether autopg is already running | `status` is now `ready`/`degraded`/`stopped`/`failed`, never `online`, so the script always re-runs `autopg install --port <candidate>`; on a host whose install is registered on another port that now fails fast ("already installed on port X; re-run with `--redeploy`") and the deploy aborts | `[[ "$(jq -r '.ready' <<<"$status")" == true ]]`, and take the port from `.port` as today |
| `deploy-personal.sh:109` | `autopg uninstall >/dev/null 2>&1 \|\| true` on the retry-on-another-port path | since v3.1.0 a non-TTY `uninstall` without `--yes` exits 2 and does nothing, so the old registration survives and the following `autopg install --port` is refused | `autopg uninstall --yes` |

### Now redundant — delete, or keep knowing it is a no-op

| Where | What it worked around | Native since |
|---|---|---|
| `deploy-personal.sh:129` `pm2 save` | install never saved the pm2 registration; without this line the `pm2-genie.service` → `pm2 resurrect` unit at boot brought back everything except autopg (#144) | v3.2.0: `install` saves when needed and verifies; `autopg doctor` → `pm2_persistence`; `status --json` → `.persisted` |
| `deploy-personal.sh:131-136` wait for `runtime.json` after `autopg install` | install returned before Postgres was up | v3.2.0: `install` returns 0 only once ready (30 s budget); check its exit code. Keep the `ExecStartPre` wait in `brain-personal.service` — that one orders boot, not install |
| `.genie/brainstorms/personal-brain-beta-triage/proposals/autopg.md` PR-1 / PR-2 | pgvector .deb 404, `uninstall --help` running the real uninstall | v3.1.0 (#147, #148) — mark the proposal done |
| `src/db/migrations/020-brain-vector-repair.sql`, `021-brain-pgvector-retry.sql`, `034-brain-pgvector-deferred-rerun.sql` | pgvector arriving after the schema because autopg's pinned .deb had been garbage-collected from pgdg (#145) | v3.1.0 (#147): with `runtime.enablePgvector=true` the extension is present from first boot. ### Already right — keep

- **External Postgres.** `DATABASE_URL` set → DSN mode, autopg discovery and the
  signed app manifest bypassed (`src/lib/db.ts:62-110`, `deploy/PORTABILITY.md`
  "External database"); unset → autopg v3 runtime discovery. That is the
  single-switch design; nothing to change. `autopg provision` / `create-app`
  are local-only and must stay out of DSN mode, as they do.
- **Signed autopg.** `deploy-personal.sh` installs through autopg's
  `install.sh`, which refuses to install unless `gh attestation verify` or
  `cosign verify-blob` succeeds, so Linux personal hosts are on signed
  binaries by construction. The macOS path (`scripts/personal-macos.ts`)
  requires a preinstalled `autopg`; the hint in `scripts/install.sh:311`
  already points at the same installer — keep it that way, never a bare
  tarball with only a sha256.
- **Signed app manifest.** `brain install --autopg` → `autopg create-app`
  material at `~/.autopg/khal_os_brain/manifest.json` (`BRAIN_AUTOPG_APP_SLUG`,
  `khal-app.json` capability `autopg:app:khal_os_brain`); runtime connections
  refuse to open without it. Unchanged in v3.2.0.
- **Runtime discovery** via `runtime.json` (`src/lib/autopg-runtime.ts`,
  `BRAIN_DB_DISCOVERY=autopg-runtime-json`) is a documented contract and is
  unchanged (`socketDir`, `port`, `pid`, `autopgPid`). For deploy-time and
  doctor checks prefer `autopg status --json` (`.ready`, `.port`,
  `.socketDir`, `.persisted`) over re-deriving liveness from the pid.
- **macOS personal** (`scripts/personal-macos.ts:640-672`): `autopg install
  --no-pm2 --no-ui --port … --socket-dir …` plus a launchd agent running
  `autopg postmaster … --pgvector`. The `--no-pm2` path has no readiness wait
  and no `pm2 save` in v3.2.0, so it behaves as before. Note that `autopg
  restart` on such a host now exits 1 naming the `external` supervisor — keep
  using `launchctl kickstart`, which the script already does. The #153 drain
  fix applies to this postmaster too.

### What brain gains without changing anything

Postgres no longer wedges after days under load (#153); pgvector auto-install
works again on Linux (#147); a pm2 daemon restart no longer loses the database
(#144, which brain had been guarding by hand); `autopg restart` actually
restarts the supervised postmaster and waits for it (#143).

## Known limits and open items

- **#149 stays open** for two policy decisions: Postgres logs still reach the
  wrapper only at `debug` level (so `autopg-server-*.log` under `~/.autopg/logs`
  stays empty), and `log_statement=all` remains the silent fallback when
  `pgaudit.so` is absent. Both change disk usage and what gets logged.
- No `linux-x64-musl` (Alpine) or `darwin-x64` (Intel macOS) tarballs.
- `autopg restart` on `systemd-user` / `launchd` hosts prints the command; it
  does not run it.
